SBD · Exercises 5 · T-SQL

Stored procedures: shop and warehouses

Short exercises on one shop database. You write procedures with parameters, return codes and results. You solve three examples together in class. Then you write six procedures on your own.

Shared database

Shop, orders and warehouses

The shop sells office equipment. Customers place orders. An order has one or more items, and customers pay for orders with payments. The shop keeps its stock in warehouses. A customer can have no orders yet. A product can be in no order. The shop also keeps inactive customers, products that it no longer sells and a closed warehouse. Their history stays in the database.

Understanding the data

Each customer has a name, a city, an email address (Email) and the flag IsActive. The email address is optional, so it can be NULL. IsActive = 0 means that the customer is inactive.

Each order has a delivery address (Address_ID) that belongs to the customer of the order. The delivery city is the city of that address. It can be different from the city of the customer.

Each product has a name, a category, a supplier, a current price (Price) and the flag IsActive. IsActive = 0 means that the shop no longer sells the product.

The table Inventory has one row for each warehouse and product: the number of units (Quantity) and the minimum stock (MinimumStock). A product with no row for a warehouse has 0 units there. A warehouse has the flag IsActive. IsActive = 0 means that the warehouse is closed. The available stock of a product is the sum of its Quantity in the active warehouses.

An order has one of these statuses: New, Paid, Shipped or Cancelled. It also has an order date (OrderDate) and a payment deadline (PaymentDueDate). Each order item has the key (Order_ID, LineNumber), a product, a quantity and the price from the day of the order (UnitPrice). The same product can be on several items of one order. The order value is the sum of Quantity × UnitPrice of the items of the order. An order with no items has the value 0.

A payment has the status Posted, Rejected or Pending. Only Posted payments count. The amount paid of an order is the sum of Amount of its Posted payments. It is 0 if the order has no such payments. The total to pay (AmountDue) of an order is the order value minus the amount paid. A value above 0 means that the customer still has to pay. A negative value means an overpayment. The order status does not change this calculation.

The table Notification stores payment reminders. A reminder has an order (Order_ID), a date (ReminderDate), a type (Type, always Payment) and a text (MessageText). An order can have only one reminder of a type for a given date. At the start the table has one row: order 1001, date 2026-10-15.

Test cases use these records on purpose: order 1011 with no items, order 1003 with the same product on two items and a delivery city different from the customer city, order 1004 with an overpayment, order 1002 with a rejected payment, inactive customer 3, customer 5 with no email address, cancelled order 1009, inactive product 550 and the closed warehouse 3 with stock. All amounts are in PLN. Ignore VAT.

How to work

  1. Run ddl_dml_5.sql in your practice database. It drops the 12 tables if they exist, creates them again and inserts the initial data. Check the row counts at the end of the script. To get the initial data back, run the file again. Your procedures stay in the database.
  2. Write each example and exercise as a procedure. Use CREATE PROCEDURE. To change a procedure that already exists, use ALTER PROCEDURE with the same name. Keep the name and the parameters from the task. End each procedure with GO.
  3. Test each procedure with EXEC calls, one call for each test case. Compare your output with the test cases below the task. Use the same numbers.
  4. Return rows with SELECT, not with PRINT. Use the return codes and OUTPUT parameters exactly as the task says.
  5. Invalid input raises an error with THROW and an error number of 50000 or more. Each task says which values are invalid. Check them first.
  6. Only Exercise 4 changes data (the table Notification). Run ddl_dml_5.sql again before each test of Exercise 4.

You solve the three examples together in class. Then you write the six exercises on your own.

An employee enters a product number and wants the details of the product with a short availability description.

Show one row with these columns: ProductID, Name, Category (the name of the category), Supplier (the name of the supplier), Price, AvailableStock and Availability.

  • Discontinued: the product is inactive (IsActive = 0). The stock does not matter.
  • Out of stock: the product is active and AvailableStock is 0.
  • Available: the product is active and AvailableStock is more than 0.

Example call

DECLARE @ReturnCode INT;
EXEC @ReturnCode = usp_GetProduct @ProductID = 101;
SELECT @ReturnCode AS ReturnCode;
Hint: steps
  1. Check the product number. Missing or not positive? Raise an error.
  2. Read the name, the price, the active flag, the category name and the supplier name of the product.
  3. No product found? Return code 1.
  4. Add up the quantity of the product in the active warehouses. No rows? The stock is 0.
  5. Inactive product? The availability is Discontinued. Otherwise, stock is 0? Out of stock. Otherwise Available.
  6. Show the row. Return code 0.

Order balance

Use in this exercise

Procedure: usp_GetOrderBalance

Parameters: @OrderID INT, @AmountDue DECIMAL(14,2) OUTPUT

Rules:

  • Set @AmountDue to NULL at the start.
  • @OrderID must be a positive number. If it is NULL or not positive, raise an error with THROW.
  • Return code 0: the order exists. Show one row.
  • Return code 1: the order does not exist. Show no rows. @AmountDue stays NULL.
  • Do not change any data.

Client brief

Customer service needs the balance of one order.

Show one row with these columns:

  • OrderID,
  • OrderValue: the sum of Quantity × UnitPrice of the items of the order (0 if there are no items),
  • AmountPaid: the sum of Amount of the payments of the order that have the status Posted (0 if there are none),
  • AmountDue: OrderValue minus AmountPaid.

Return AmountDue also in the OUTPUT parameter. A negative AmountDue is an overpayment: keep it. Do not skip cancelled orders and do not change any status.

Calculate OrderValue and AmountPaid in two separate queries. If you join the items and the payments in one query, the amounts are counted too many times.

Example call

DECLARE @ReturnCode INT, @Balance DECIMAL(14,2);
EXEC @ReturnCode = usp_GetOrderBalance @OrderID = 1001, @AmountDue = @Balance OUTPUT;
SELECT @ReturnCode AS ReturnCode, @Balance AS AmountDue;
Hint: steps
  1. Check the order number. Missing or not positive? Raise an error.
  2. Order not found? Set nothing and return code 1.
  3. Add up the value of the items. No items? The value is 0.
  4. Add up the posted payments only. No payments? The amount is 0.
  5. Subtract the amount paid from the order value.
  6. Show the row. Return code 0.

Rules:

Client brief

The payments department wants a reminder for each late order. The procedure only saves the reminder in Notification. It does not send anything.

Go through the orders one by one, with a cursor, in the order of the order number (the column ID of Orders).   • Skipped: the customer has no email address (Email is NULL), or Notification already has a reminder with the same order, the same ReminderDate (@AsOfDate) and the type Payment.

The text has the order number and the total to pay with two decimal places. At the end show one row with the columns CreatedCount and SkippedCount. A second call with the same date must not create any duplicate.

Procedure: usp_PlanReplenishment

Parameters: @WarehouseID INT, @Budget DECIMAL(12,2)

Rules:

  • @WarehouseID must be a positive number. @Budget must not be NULL or negative. Otherwise raise an error with THROW.
  • A warehouse that does not exist has no rows in Inventory: show an empty result.
  • Return code 0. Do not change any data.

Client brief

The warehouse manager has a limited budget. Prepare a purchase list for one warehouse.

Use a cursor over the rows of Inventory for this warehouse. Take only rows where the product is active (IsActive = 1) and Quantity is less than MinimumStock. Go through them in the order of Product_ID. Keep the budget left in a variable. At the start it is @Budget. For each row:

  • The quantity needed is MinimumStock minus Quantity.
  • The quantity affordable is the largest whole number of units that the budget left can pay at the Price of the product.
  • The quantity to buy is the smaller of the two numbers.
  • The quantity to buy is 0? Skip the product and go on with the next one. Do not stop.
  • Otherwise save the product with its quantity to buy and its cost (quantity to buy × Price). Subtract the cost from the budget left.

At the end show the saved rows with these columns: ProductID, Name, QuantityToBuy, Price and Cost. Order them by ProductID.

EXEC usp_PlanReplenishment @WarehouseID = 1, @Budget = 500;

Exercise 6 · Payments department

Instalment plan

Use in this exercise

Procedure: usp_SplitAmount

Parameters: @Amount DECIMAL(12,2), @InstalmentCount INT, @FirstDate DATE

Rules:

  • @Amount must be more than 0. @InstalmentCount must be from 1 to 12. @FirstDate must not be NULL. If any of these rules is broken, raise an error with THROW.
  • This procedure does not read any table. Return code 0.

Client brief

The client wants to split an amount into monthly instalments. The instalments must add up to exactly @Amount.

  • Work in grosz (1 PLN = 100 grosz). Convert @Amount to a whole number of grosz.
  • Divide the grosz by @InstalmentCount with whole-number division. This is the base instalment.
  • Every instalment has the base amount, except the last one. The last instalment has the base amount plus the whole remainder of the division.
  • The deadline of instalment number n is the date n − 1 months after @FirstDate. Always count from @FirstDate, not from the previous instalment.

Show one row for each instalment with these columns: InstalmentNumber, DueDate (the deadline of the instalment) and InstalmentAmount (in PLN, with two decimal places). Order them by InstalmentNumber.

EXEC usp_SplitAmount @Amount = 220.00, @InstalmentCount = 3, @FirstDate = '20261031';

  2. Convert the amount to whole grosz.
